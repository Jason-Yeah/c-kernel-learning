# C++ 设计模式学习项目

本项目使用 C++14 及以上标准学习面向对象设计原则、UML 和 GoF 23 种设计模式，并提供各模式的独立说明、示例代码以及综合实战。

设计模式不是固定代码模板，也不是必须全部使用的“标准答案”。它们是对常见设计问题的命名和经验总结。学习时应先理解需求中的变化，再判断某个模式能否降低耦合、保护稳定代码或改善对象协作。

## 一、面向对象设计原则

原则用于判断设计质量，模式则是落实原则的常见方案。不要为了遵守原则而无条件增加抽象；只有当抽象能隔离真实变化时，它才有价值。

### SOLID 与迪米特法则

| 原则 | 核心含义 | 适合应用的信号 | 常见误区 |
|---|---|---|---|
| 单一职责原则（SRP） | 一个模块应只有一个主要变化原因 | 一个类同时处理业务、存储、日志、网络等多类职责 | 不是要求“一个类只能有一个方法”，而是让相关职责内聚 |
| 开闭原则（OCP） | 对扩展开放，对修改关闭 | 每增加一种策略或类型都要修改稳定的条件分支 | 不应预测所有未来需求并预先建立庞大抽象 |
| 里氏替换原则（LSP） | 子类型必须能安全替换父类型 | 子类重写后改变前置条件、后置条件或抛出“不支持”异常 | 只有代码复用关系不代表存在真正的继承关系 |
| 接口隔离原则（ISP） | 客户端不应依赖不需要的方法 | 接口很大，实现类被迫提供空实现 | 不能把接口拆成毫无业务意义的单方法碎片 |
| 依赖倒置原则（DIP） | 高层策略和低层细节共同依赖抽象 | 业务代码直接创建数据库、支付 SDK、文件系统等具体对象 | 抽象应由业务需求驱动，不是给每个类机械添加接口 |
| 迪米特法则（LoD） | 对象只与必要的直接协作者通信 | 出现很长的调用链，如 `a.getB().getC().doWork()` | 不能把所有行为都转发给一个上帝对象 |

详细说明与示例见：[SOLID + LoD](docs/base_principles.md)。

### 贯穿本项目的设计观念

- **封装变化：** 把频繁变化的算法、外部接口、创建过程或状态规则放到独立对象中。
- **面向接口编程：** 高层模块依赖稳定能力，不依赖某个具体实现的细节。
- **组合优于继承：** 需要运行时替换行为，或不存在严格的“是一个”关系时，优先组合对象。
- **高内聚、低耦合：** 一个类内部职责相关，对外只暴露完成协作所需的最小接口。
- **优先保证正确性和简单性：** 没有实际变化需求时，直接、清晰的代码通常优于过早抽象。

## 二、创建型模式

创建型模式关注“对象如何被创建”，用于隐藏复杂构造过程、解耦客户端与具体类型，或者控制对象的创建数量。

### 快速总览

| 模式 | 解决的问题 | 何时适合应用 | 慎用情况 |
|---|---|---|---|
| 简单工厂 | 根据参数集中创建不同产品 | 产品较少、创建逻辑简单，希望移除客户端中的 `new` 和分支 | 产品频繁增加时，工厂本身会不断修改；它不属于 GoF 23 种模式 |
| Factory Method（工厂方法） | 让子类或具体创建器决定创建哪种产品 | 框架只知道产品接口，具体产品由扩展者决定 | 产品固定且构造简单时会产生多余创建器层次 |
| Abstract Factory（抽象工厂） | 创建一组相互匹配的产品族 | UI 主题、跨平台组件、数据库驱动等必须成套切换 | 只增加单个新产品时，需要修改所有具体工厂 |
| Builder（建造者） | 分步骤构造复杂对象 | 参数很多、存在可选字段、创建顺序重要或需要不同表示 | 对象只有少量必填参数时，普通构造函数更直接 |
| Prototype（原型） | 通过复制既有对象创建新对象 | 创建成本高、类型在运行时确定，或对象配置大部分相同 | 深浅拷贝、资源句柄和循环引用不明确时风险较高 |
| Singleton（单例） | 保证进程内只有一个实例并提供访问点 | 确实存在唯一资源或全局协调点，且生命周期明确 | 容易成为隐藏全局变量，降低可测试性并引入并发问题 |

### 工厂模式如何选择

```text
只是集中一小段创建分支                 -> 简单工厂
希望扩展者决定创建哪一个产品           -> 工厂方法
必须一起创建并切换多个相关产品          -> 抽象工厂
同一复杂对象需要分步骤或多种配置方式    -> 建造者
创建新对象的主要方式是复制现有对象      -> 原型
```

## 三、结构型模式

结构型模式关注“类和对象如何组合”。它们常用于兼容外部接口、组织树形结构、动态叠加能力或降低客户端面对的系统复杂度。

### 快速总览

| 模式 | 解决的问题 | 何时适合应用 | 慎用情况 |
|---|---|---|---|
| Adapter（适配器） | 将不兼容接口转换为系统需要的接口 | 接入旧代码、第三方 SDK 或不同数据协议 | 如果可以直接统一接口，不要额外增加转换层 |
| Bridge（桥接） | 将两个独立变化的维度分离并组合 | 抽象与实现都需要扩展，如消息类型 × 发送渠道 | 只有一个变化维度时，普通组合或策略通常足够 |
| Composite（组合） | 统一处理叶节点与容器节点 | 文件树、组织架构、UI 树、表达式树 | 叶节点与容器行为差异极大时，统一接口可能变得牵强 |
| Decorator（装饰） | 运行时按需叠加对象能力 | IO 流、消息增强、缓存、压缩、权限等可组合功能 | 装饰层过多会使调试和对象身份判断变复杂 |
| Facade（外观） | 为复杂子系统提供简单入口 | 客户端不应了解多个子系统的调用顺序 | 外观不应吸收所有业务而演变成上帝对象 |
| Flyweight（享元） | 共享大量对象中的重复不可变状态 | 字符、棋子、树木、文件类型等对象数量巨大 | 对象数量少或状态难以安全拆分时收益不大 |
| Proxy（代理） | 在不改变服务接口的情况下控制访问 | 权限、缓存、延迟加载、远程调用、日志 | 额外间接层可能隐藏网络或性能成本 |

### 容易混淆的结构型模式

- **适配器 vs 桥接：** 适配器通常用于事后兼容已有接口；桥接通常在设计阶段主动拆分两个变化维度。
- **装饰 vs 代理：** 装饰器强调叠加新能力；代理强调控制对原对象的访问。
- **外观 vs 适配器：** 外观简化一组复杂接口；适配器转换一个不兼容接口。
- **组合 vs 装饰：** 组合形成树并统一叶子与容器；装饰通常形成链并增强单个对象。

## 四、行为型模式

行为型模式关注“对象之间如何分工、通信以及分配算法”。它们适合处理可替换算法、状态流转、请求调度、事件通知和复杂协作关系。

### 快速总览

| 模式 | 解决的问题 | 何时适合应用 | 慎用情况 |
|---|---|---|---|
| Chain of Responsibility（责任链） | 让请求依次经过多个处理器 | 校验、审批、过滤器、中间件，处理顺序需配置 | 必须保证某个处理器执行时，要处理“无人处理”的结果 |
| Command（命令） | 把请求封装为对象 | 需要排队、日志、重试、撤销、宏命令 | 只调用一次且不需要管理请求时会增加类型数量 |
| Interpreter（解释器） | 用对象表示并解释一套小型语法 | 规则表达式简单稳定，且需要组合和执行 | 完整语言或复杂文法应使用解析器生成器或成熟引擎 |
| Iterator（迭代器） | 不暴露内部结构地顺序访问集合 | 自定义容器需要统一遍历方式 | 标准容器已有成熟迭代器时无需重复实现 |
| Mediator（中介者） | 集中协调多个对象之间的复杂交互 | GUI 控件、聊天室、流程组件形成网状依赖 | 中介者容易承载过多规则并成为上帝对象 |
| Memento（备忘录） | 在不破坏封装的情况下保存和恢复状态 | 编辑器撤销、游戏存档、事务快照 | 状态体积大或快照频繁时要考虑内存和持久化成本 |
| Observer（观察者） | 一对多广播状态变化 | 事件系统、MVC、数据订阅、领域事件 | 要处理订阅者生命周期、通知顺序、异常和线程安全 |
| State（状态） | 将依赖当前状态的行为分散到状态对象 | 订单、连接、播放器等有明确状态图与合法转换 | 状态很少且逻辑简单时，枚举配合条件判断更清楚 |
| Strategy（策略） | 封装并替换同一目标的不同算法 | 定价、排序、压缩、路由等算法需独立切换 | 算法不会变化或差别只是一个常量时无需建类层次 |
| Template Method（模板方法） | 在基类中固定流程骨架，让子类实现步骤 | 算法步骤顺序稳定，部分步骤需要定制 | 需要运行时自由组合步骤时，组合与策略更灵活 |
| Visitor（访问者） | 在不修改对象结构的情况下增加操作 | AST、文件树等节点类型稳定而操作经常增加 | 节点类型经常变化时，所有访问者都需要同步修改 |

### 容易混淆的行为型模式

- **策略 vs 状态：** 策略通常由客户端选择算法；状态由对象内部生命周期推动，并决定当前允许的行为。
- **策略 vs 命令：** 策略回答“怎样完成计算”；命令表示“要执行什么请求”，并可被存储、排队或撤销。
- **模板方法 vs 策略：** 模板方法依赖继承复用固定骨架；策略通过组合替换整个算法或步骤。
- **观察者 vs 中介者：** 观察者负责事件广播，不关心完整业务流程；中介者明确协调多个同事对象的交互。
- **命令 + 备忘录：** 命令记录操作，备忘录保存状态，两者经常共同实现撤销，但并非必须绑定使用。

## 五、按问题选择模式

遇到具体需求时，可以先根据“问题信号”缩小选择范围：

| 问题信号 | 优先考虑 |
|---|---|
| 创建过程复杂、参数很多 | Builder |
| 需要创建一组匹配的对象 | Abstract Factory |
| 需要接入不兼容的已有接口 | Adapter |
| 两个维度都可能独立扩展 | Bridge |
| 需要动态叠加多项能力 | Decorator |
| 需要简化复杂子系统的使用 | Facade |
| 同类小对象数量极大、重复状态很多 | Flyweight |
| 访问服务前后需要权限、缓存或日志 | Proxy |
| 多个校验或处理步骤需要按顺序短路 | Chain of Responsibility |
| 请求需要排队、撤销、重试或审计 | Command |
| 多个对象之间形成复杂网状通信 | Mediator |
| 一个事件需要通知多个独立对象 | Observer |
| 对象行为由当前状态和状态图决定 | State |
| 同一业务目标存在多种可替换算法 | Strategy |
| 流程骨架稳定、部分步骤允许定制 | Template Method |
| 对稳定对象结构频繁增加新操作 | Visitor |

这张表只是候选提示，不是自动选型规则。确定模式前还应回答：

1. 这里是否真的存在变化？
2. 变化是否会独立发生？
3. 当前简单方案已经造成了什么问题？
4. 引入抽象后的维护成本是否低于它解决的问题？
5. 能否用更小的接口、更直接的组合或一个普通函数解决？

## 六、C++ 实现关注点

设计模式描述的是对象关系，C++ 实现还必须明确资源和生命周期。

- 抽象基类应提供虚析构函数，例如 `virtual ~Strategy() = default;`。
- 独占多态对象优先使用 `std::unique_ptr`，共享不可变对象可使用 `std::shared_ptr<const T>`。
- 非拥有型引用和指针必须保证目标对象的生命周期；观察者尤其需要防止悬空引用。
- 能用值语义表达的简单策略，不一定需要堆分配或继承，也可使用函数对象、模板或 `std::function`。
- 使用 `override` 检查虚函数重写，使用 `final` 表达不再派生的具体实现。
- 不要在构造函数和析构函数中依赖虚函数的多态行为。
- 多线程单例、观察者通知、命令队列和共享享元需要额外考虑同步与异常安全。
- 示例为了集中展示模式可能采用单文件；实际项目应按稳定接口、实现和用例拆分 `.hpp/.cpp`。

通用编译方式：

```bash
g++ -std=c++14 -Wall -Wextra -pedantic main.cpp -o demo
./demo
```

若某个示例包含多个 `.cpp` 文件，应将它们一起传给编译器，或使用示例目录内的 CMake 配置。

## 七、推荐学习路线

1. 阅读 SOLID、迪米特法则和 UML，掌握组合、聚合、继承、实现与依赖关系。
2. 学习 Strategy、Factory Method、Adapter、Observer，这些模式较容易映射到日常开发。
3. 学习 Decorator、Composite、Command、State，理解对象组合和行为协作。
4. 学习 Abstract Factory、Builder、Facade、Proxy、Template Method。
5. 最后学习 Bridge、Flyweight、Mediator、Memento、Interpreter、Visitor 等适用边界更明确的模式。
6. 不看原代码重新实现一个模式，并用新增需求检验是否真正做到低耦合扩展。
7. 完成 [设计模式综合实战](finial/finial.md)，重点阅读其中的开发分析思路、UML 和失败路径。

学习完成后，应能够回答的不只是“这是什么模式”，还包括：

- 它保护了哪部分稳定代码？
- 它隔离了什么变化？
- 对象之间的所有权和依赖方向是什么？
- 不使用它时，最简单的替代方案是什么？
- 当前业务规模是否值得承担它带来的额外复杂度？

最终目标是形成面向对象分析能力：让职责清晰的对象通过最小接口协作，并根据真实变化选择足够简单的设计。
