## 0. 从客户端到内核：先建立整体图

客户端调用 `connect` 后，内核完成 TCP 握手并在服务端监听 socket 的队列中管理连接。服务端 `accept` 得到新的连接 fd。收到的数据先进入内核 socket 接收缓冲区；`recv/read` 把数据交给应用缓冲区，应用解析协议、执行业务，再通过 `send/write` 把响应交给内核发送缓冲区。内核随后处理 TCP、拥塞控制和网卡发送。

```text
客户端程序 ──TCP──> 服务端网卡/协议栈/内核缓冲区
                          │ accept / epoll_wait
                          ▼
                I/O 事件循环（主线程）
                    │任务队列
                    ▼
             工作线程：协议/业务逻辑
                    │响应完成通知
                    └──────────────> 事件循环注册可写并发送
```

Linux fd 是进程 fd 表里的整数索引，不是连接内容。一个连接通常由一个 fd 引用内核 socket 状态。阻塞调用暂时不能完成时会睡眠等待；非阻塞调用立即返回，但 `EAGAIN` 代表现在没有进展，不是程序故障也不是数据已经处理。

网络 I/O 中所谓“就绪”是现在可以尝试读或写；“完成”是某次异步读写已由内核执行完毕。一次 `recv` 可以只返回半个请求，一次 `send` 也可能只发送部分数据。TCP 只提供有序字节流，消息边界必须由应用协议定义。

### 先看程序要实现的工作

配套服务器监听 `127.0.0.1`，每个请求是一行 UTF-8/ASCII 文本，以换行结束；工作线程将 ASCII 小写字母变成大写，服务器回复 `OK <结果>\n`。例如：

```text
客户端发送：hello server\n
服务端回复：OK HELLO SERVER\n
```

它一次只允许每条连接有一个业务请求在处理，处理完成后才继续读下一行。这让回复顺序清楚，也体现了用背压限制单连接在途工作量。

## 8.1 服务器模型

**原书 PDF 第 265～270 页**：介绍 C/S，并画出 TCP 客户端/服务器的典型流程：服务器创建、绑定、监听 socket，等待连接，accept 后分配逻辑单元；客户端 connect，发送请求，读取响应。接着介绍 P2P，指出纯 P2P 的节点发现困难，现实中可用专门发现服务器。

### 8.1.1 C/S（客户端/服务器）

客户端提出请求，服务器提供集中服务。服务器启动后持续运行，多个客户端可以同时连接。客户端/服务器是应用角色，不是 TCP/IP 协议中的固定身份：TCP 两端都能主动关闭，也都能收发数据；哪边调用 listen 取决于应用架构。

串行服务器先完整处理客户 A，再处理客户 B。若 A 等待磁盘或数据库，B 也只能等待。常见服务器因此把连接等待、I/O 和业务处理拆开，使用多路 I/O 等待和并发工作单元。

**现代 C++ 实践**：将“连接生命周期”“协议解析”“业务逻辑”分成单独组件。C++ 类可以表达连接和请求，但并不自动带来并发安全。监听 fd、已连接 fd、请求缓冲区各自需要明确所有者和关闭时机。连接断开后仍在执行的业务任务也要有取消/结果丢弃策略。

### 8.1.2 P2P（点对点）

P2P 节点既使用服务也提供服务，资源可分散共享，但节点发现、NAT 穿透、信任和流量调度都更复杂。原书指出纯 P2P 互相发现困难，因此实际系统常加入发现/目录服务器。云集群也能体现资源分布，但不是所有云服务都采用 P2P。

从单机程序设计看，一台 P2P 主机仍可能同时实现客户端和服务器端，所以 socket、连接、协议处理等 C/S 基础仍有用。

## 8.2 服务器编程框架

**原书 PDF 第 271～273 页**：把服务器抽象为 I/O 处理单元、逻辑单元、网络存储单元、请求队列。I/O 单元接受连接和收发数据；逻辑单元处理请求；存储单元可以是文件、数据库或缓存；请求队列把接入与业务连接起来。集群里接入层还可做负载均衡。

| 单元 | 初学者理解 | 配套服务器里的对应部分 |
|---|---|---|
| I/O 处理 | 谁在等连接、读数据、写响应 | 主线程中的 epoll 事件循环 |
| 逻辑处理 | 请求要做什么 | 线程池中的 ASCII 大写转换 |
| 网络存储 | 请求处理需要访问的数据 | 本实验没有存储依赖 |
| 请求队列 | I/O 和业务线程交接任务的地方 | mutex + condition_variable 保护的 job queue |

真实服务还会有协议层、鉴权、配置、日志/指标、超时、限流、存储访问和优雅关停。请求队列不能无限增长：若接入速度持续高于业务处理速度，内存会逐渐耗尽。生产系统通常给队列设置容量，达到上限时暂停读取、拒绝新工作或返回过载错误。

现代 C++ 可把请求对象做成值类型并通过移动减少复制；但对象进入异步队列后，其数据必须拥有足够长的生命周期。把 `string_view` 或 `span` 指向临时栈缓冲区再交给工作线程，是典型悬空引用错误。

## 8.3 I/O 模型

**原书 PDF 第 274～276 页**：区分阻塞/非阻塞，并介绍阻塞 I/O、I/O 复用、信号驱动 I/O、异步 I/O。书中总结：同步 I/O 的数据移动由应用发起；异步 I/O 的读写由内核执行并在完成后通知。这个“就绪/完成”区分很重要。

### 阻塞 I/O

对阻塞 socket 调用 `recv` 时，如果还没有数据，线程会睡眠；数据到达后内核唤醒线程，`recv` 返回数据。好处是控制流简单；坏处是每个等待中的连接若对应一个线程，会占用线程栈、调度成本和内存。

### 非阻塞 I/O

非阻塞 fd 上调用 `recv`，无数据时立即返回 `-1`，`errno` 为 `EAGAIN/EWOULDBLOCK`。这表示“现在读不到”，应等事件通知后再试，不能紧密循环空转。`connect` 非阻塞时常以 `EINPROGRESS` 表示连接正在建立。

`O_NONBLOCK` 是 fd 所引用 open file description 的状态标志；dup 出来的 fd 通常共享该状态。设置前应用要清楚是否还有其他组件持有同一 open file description。

### I/O 多路复用

`select/poll/epoll` 让一个线程等待很多 fd 的事件。等待函数本身可以阻塞，直到任意一个 fd 就绪；这仍然不意味着连接 fd 上的读写必须阻塞。典型模式是连接 fd 设为非阻塞，epoll 报告可读后循环 recv 直到 `EAGAIN`。

epoll 是 Linux 接口。水平触发（LT）在条件仍成立时持续通知，较容易入门；边沿触发（ET）通知状态变化，应用通常必须把数据读到 `EAGAIN`，否则可能没有下一次边沿可处理。配套示例用 LT，先学习状态和生命周期。

### 信号驱动 I/O 与异步 I/O

信号驱动 I/O 可用 SIGIO 通知 fd 有事件；信号处理函数受异步信号安全规则限制，复杂工作通常转交事件循环。POSIX AIO 接口由 `<aio.h>` 定义，但 Linux socket 上的支持、实现方式和性能特征与文件 AIO 不可一概而论。现代 Linux 网络服务最常见的是 epoll、io_uring 或成熟异步运行时，而非把所有 socket 操作建立在 POSIX AIO 上。

C++20 协程是语言机制：它可以暂停和恢复函数，但必须有 I/O 运行时把 epoll/io_uring 完成事件接到协程恢复上。`co_await recv()` 不是标准库自带网络操作。

## 8.4 Reactor 与 Proactor

**原书 PDF 第 277～283 页**：介绍 Reactor（通知就绪，由应用读写）和 Proactor（内核完成读写后通知），并给出用同步 I/O 模拟 Proactor 的流程。

### Reactor：事件就绪，应用处理 I/O

```text
epoll_wait 报告 fd 可读 → 应用线程 recv → 组装请求 → 业务处理
业务产生响应 → 应用等待可写 → 应用线程 send
```

原书的 Reactor 示例让主线程监测事件，再把事件放入队列，由工作线程完成读写和业务。现代实现也常由 I/O 线程独占连接状态，工作线程只做 CPU/阻塞业务，完成后通过 eventfd/消息队列把结果送回 I/O 线程。这能避免多个线程同时修改同一连接缓冲区。

### Proactor：操作完成后通知

应用预先提交读操作及缓冲区，内核/运行时完成数据复制后通知应用；工作线程拿到完整读结果执行业务，再提交写操作。通知针对“操作完成”，不是“可以尝试操作”。实现依赖所用操作系统和具体 API。

### 同步 I/O 模拟 Proactor

主线程收到可读事件后亲自循环读取到 `EAGAIN`，把已经读取的数据对象投递给业务线程。业务线程只处理完整请求对象，不再碰 socket。业务完成后把响应交回 I/O 线程，由其负责写出。对逻辑线程而言，像是得到了一次已完成的读取；底层仍然是 readiness + 同步 recv。

**本例是什么模式？** 主线程使用 epoll 监听并执行 recv/send，工作线程只转换业务字符串，结果经 eventfd 返回主线程。因此它是 **Reactor 风格的 I/O 所有权 + 工作线程池**，局部上让工作线程收到的是已读取完成的请求对象，类似原书“模拟 Proactor”的分工。不要把它说成内核异步 I/O Proactor。

## 8.5 并发模式

**原书 PDF 第 284～294 页**：提醒并发模式里的同步/异步，含义与 I/O 模型里的同步/异步不同；介绍半同步/半异步及其半同步/半反应堆变体，以及 Leader/Follower 线程轮流担任领导者。

### 两种“同步/异步”不要混在一起

I/O 语境讨论谁执行读写以及通知就绪还是完成；并发模式语境讨论程序按顺序主动执行，还是由系统事件回调驱动。两套术语回答不同问题。一个服务器可以使用同步工作线程处理业务，同时使用 epoll 异步等待 I/O 事件。

### 半同步/半异步与半同步/半反应堆

原书的半同步/半异步由事件驱动的 I/O 单元把任务放入请求队列，同步工作线程取出并处理。半同步/半反应堆中，主线程监听并把连接/就绪事件入队，工作线程竞争队列锁取任务。简单易懂，但共享队列需要同步；一个工作线程在处理一个连接期间无法同时服务别的连接；队列积压会增加延迟。

原书还介绍更高效的一种结构：主线程只接受新连接并把 fd 派给某个工作线程；工作线程各自运行 epoll 循环管理自己的一批连接。这样减少共享连接状态和中心队列竞争，但 fd 派发、线程退出、负载平衡和跨线程唤醒更复杂。

### Leader/Follower（领导者/追随者）

多个线程共享一个事件源集合。任一时刻一个线程当 Leader 等待事件；事件到来后它处理或交给其他线程，同时选出新的 Leader。优点是减少中心任务队列和锁竞争；缺点是实现复杂、事件源集合的所有权/同步要求高，也不一定适合“每个线程管理自己 epoll”的结构。

现代项目通常先选择简单明确的模型：一个或少数 I/O event loop + 有界工作池，或成熟的异步运行时。只有 profile 显示共享锁、唤醒和队列成为瓶颈，再考虑 per-core event loop、SO_REUSEPORT、无锁队列等方案。模型名不保证性能。

### 本例的线程怎样交接

```text
I/O 主线程：accept/epoll/recv ── Job{连接, 一行} ──> 有界概念上的线程池
I/O 主线程：epoll 等 eventfd <── Completion{连接, 响应} ── 工作线程
I/O 主线程：epoll 注册 EPOLLOUT 并 send
```

示例使用 `std::mutex` 和 `std::condition_variable` 实现生产者/消费者队列。worker 不直接写 socket，也不修改连接对象状态，因此连接缓冲区由 I/O 线程独占。代码为教学未给任务队列设置容量，生产环境必须补上有界队列和过载策略。

## 8.6 有限状态机

**原书 PDF 第 295～306 页**：先举按包类型分支的状态机，再解释显式状态转移；重点示范 HTTP 请求的主状态机（请求行/头部）与从状态机（逐字节识别 CRLF、行未完整或格式错误）。HTTP 请求头以空行结束，TCP read 可能只获得部分行。

有限状态机（FSM）由有限个状态、输入、转移规则和动作组成。当前状态加输入决定下一状态和操作。与散落的 boolean 条件相比，状态图能明确哪些操作允许发生、错误如何退出。

本例连接状态：

```text
Reading --收到完整换行请求并投递工作--> Processing
Processing --eventfd 通知业务完成--> Writing
Writing --响应全部发送--> Reading
任意活动状态 --错误/超长/结束条件--> Closed
```

收到部分行时仍在 Reading，数据保留在 `std::string input`；找到换行才抽出请求。若 worker 还在处理，主线程暂时停掉该连接的 EPOLLIN，避免无界堆积。写响应时维护 `sent` 偏移，应对短写；写到 `EAGAIN` 等下一次 EPOLLOUT。

HTTP 解析器通常要更细：请求行、头字段、消息体长度/分块编码、keep-alive、错误码等。原书主/从状态机思路仍有帮助，但示例代码不可直接用于公网 HTTP：它只接收简单文本行，不实现 HTTP、TLS、认证或恶意输入防护。

**现代 C++ 表达**：可用 `enum class State` 避免枚举值意外转换，用成员变量保存每连接状态；用 `std::string` 拥有缓冲，`std::string_view` 做短期解析视图。若视图跨异步任务存活，必须确保源字符串不被修改/释放。C++20 `std::variant` 可表示不同状态携带不同数据，但不必为了使用新语法而强行复杂化。

## 8.7 性能建议

**原书 PDF 第 307～311 页**：从资源池、减少数据复制、减少上下文切换与锁竞争三方面提出建议。主要原则在今天依旧适用，但需要通过负载和延迟测量验证。

### 8.7.1 池

池预先创建资源，减少请求路径上的分配和创建成本。常见有对象/内存池、线程池、进程池、数据库连接池。代价是常驻内存、容量管理、空闲资源清理和复用对象残留状态风险。

现代实践中，先测分配是否在热点；标准分配器通常已很快。C++17 `std::pmr` 提供多态内存资源接口，可将对象分配委托给池资源；`std::pmr::monotonic_buffer_resource` 适合一批对象统一释放，线程安全性须按具体资源类型确认。线程池容量、连接池最大连接数都要有界和监控。

### 8.7.2 减少复制

原书以 sendfile、进程间共享内存和解析时用索引而非复制子串为例。用户态到内核态的数据复制会消耗带宽与 CPU；小对象复制未必是热点，优先减少大块、不必要的复制。

C++ 的移动语义可以转移容器/字符串资源所有权，`std::string_view/span` 可以无复制观察数据，但要求生命周期正确。`sendfile`、`splice` 等内核接口受 fd 组合限制；TLS 加密、压缩、业务解析可能需要访问数据，从而改变可用路径。“零拷贝”不是绝对没有复制，也不能据此推断更快。

### 8.7.3 上下文切换和锁

每个连接创建线程会导致大量线程栈、调度与上下文切换。线程池能复用有限 worker；epoll event loop 可让少数 I/O 线程管理许多连接。线程数并非“永远不超过 CPU 核心数”：阻塞 I/O、CPU 任务、运行时和内核调度目标不同，应测量设定。

锁保护共享状态，但竞争严重时会让线程等待。先通过线程所有权减少共享，再考虑缩小锁粒度或读写锁；读写锁本身也有开销和饥饿风险。无锁算法更复杂，不是默认更快。

建议观察吞吐量、P50/P95/P99 延迟、CPU 利用率、上下文切换、队列等待时间、fd/内存和错误率。压测要包含慢客户端、突发连接、长请求及系统负载，回环 echo 不能代表生产网络。

## 9. C++11～20 落地方式

| 语言能力 | 可用于框架的地方 | 注意事项 |
|---|---|---|
| C++11 RAII、移动、`std::thread`、mutex/condition_variable | fd、线程池、任务所有权 | Linux epoll 仍是原始 fd API；析构与关停顺序很重要 |
| C++14 泛型 lambda | 简化回调和任务包装 | 不会自动解决回调生命周期 |
| C++17 `string_view`、`variant`、`pmr`、`filesystem` | 解析视图、状态值、分配策略 | view 非拥有；PMR 资源的线程安全需核实 |
| C++20 `jthread`、stop token、concept、协程 | 可取消线程、接口约束、异步控制流 | 协程需要 scheduler/I/O runtime；`jthread` stop token 不会自动取消阻塞系统调用 |

本例为突出概念，使用 `std::thread` 加显式停止标志，线程池析构时通知并 join worker。生产代码可用 `std::jthread` 管理线程生命周期，但还需用 eventfd/关闭队列等机制唤醒等待中的线程；仅请求 stop 不会自动唤醒普通 condition_variable。

现代服务器实际常选成熟网络库/运行时来承担事件循环、定时器、取消、缓冲区和 TLS 集成；无论使用哪种库，C/S 模型、就绪/完成、背压、状态机和资源生命周期这些概念仍然适用。

编译运行方法、客户端命令和完整源码导读见[配套 README](../code/base_server_application_framework/readme.md)。
