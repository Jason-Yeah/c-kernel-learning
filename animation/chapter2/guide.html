整数与C位运算：先看类型，再解释位串

第2章目录 · C位运算动画 · 补码／转换／溢出动画 · 字节序

本节是第2章的下一部分，不是全章已完成。浮点表示与舍入仍未开展。两部新动画共用一份完整C程序、一次实际GDB运行的17个停点和原样命令输出。数据离线播放，网页不会运行C或实时控制GDB。

实验限定为Linux x86-64、C11、8-bit byte、32-bit int、32-bit unsigned int。类型、位宽、变量地址和对象字节实际采集；按位推导、箭头与教学速度不是CPU内部时钟。位权图横向从高位到低位，不是内存地址图；实验台的字节则按地址升序显示。

1. C位运算的六个符号

对两个整数，位运算按对应二进制位组合。下面先看单个位的真值表。

abAND（两位都为1）OR（至少一位为1）XOR（两位不同）
00000
01011
10011
11110
r_and = bits & mask;   /* 按位与：掩码为0的位清零。 */
r_or  = bits | mask;   /* 按位或：掩码为1的位设为1。 */
r_xor = bits ^ mask;   /* 按位异或：掩码为1的位翻转；^不是乘方。 */
r_not = ~bits;         /* 按位取反：反转运算类型的所有位。 */
r_left  = bits << 2;   /* 左移：向高位移动，右侧补0。 */
r_right = bits >> 2;   /* 无符号右移：向低位移动，左侧补0。 */

本次实际输入为uint32_t的bits=0x000000B6、mask=0x0000000F。低8位是10110110和00001111，但两者的运算宽度都是32位，不能把低8位近景误当成整个对象。

实际表达式GDB记录的结果注意点
bits & mask0x00000006提取低4位
按位或（见上方C代码）0x000000BF把低4位全部置1
bits ^ mask0x000000B9翻转低4位
~bits0xFFFFFF49高24位也翻转，不是只有0x49
bits << 20x000002D8进入bit9的1没有越过32位边界，不能只保留D8
bits >> 20x0000002D无符号高位补0

位运算不是逻辑运算

&和|组合整数的每一位；&&和||先把操作数视为真／假，结果类型为int，值只有0或1。逻辑与／或还具有短路规则，不能在有副作用时随意互换。

本次bits与mask都非0，所以bits && mask实际为1，而bits & mask实际为6。!bits是逻辑取反，实际为0；~bits是32位按位取反。写掩码判断时加括号，例如(bits & mask) != 0，不要依靠记忆中的优先级猜含义。

简单掩码写法

以下额外小例说明常用写法；动画实际采集的是上面的bits／mask那组，不把这些额外写法冒充另有GDB停点。

uint32_t x = UINT32_C(0xB6);
uint32_t low = x & UINT32_C(0x0F);          /* 0x06 */
uint32_t set = x | (UINT32_C(1) << 3);      /* 0xBE：设bit3 */
uint32_t clear = x & ~(UINT32_C(1) << 1);   /* 0xB4：清bit1 */
uint32_t toggle = x ^ (UINT32_C(1) << 5);   /* 0x96：翻bit5 */
int bit5 = (x & (UINT32_C(1) << 5)) != 0;  /* 1：测试bit5 */

这里bit0指最低有效位，不是“最低内存地址上的第一个bit”。位权和字节序是不同问题。移位计数3、1、5都在本例32位运算的有效范围内。

2. 小整型通常先提升为int

在本机，uint8_t是unsigned char，能表示0…255；int能覆盖这个范围。因此它参与~、移位、加法等运算前，通常先做整型提升，成为32-bit int。

uint8_t small = 0xB6;
promoted_not = ~small;                /* int，实际-183 */
narrow_not = (uint8_t)promoted_not;    /* 显式转unsigned 8位，实际0x49 */
small_shift = small << 8;             /* int，实际0x0000B600 */

这不是“8位的~直接得到8位49”。本次GDB的whatis ~small和whatis small << 8都给出int，实际位宽32。动画同时保留uint32_t的~bits和独立uint8_t的small：同样的32位形状FFFFFF49，可以有不同的有符号解释。

small << 8在本例合法：左操作数提升后的类型是32位int，182乘256为46592，也可表示。不能只因源变量占8位，就说“移8位一定非法”。对于更复杂的混合类型表达式，还要继续考虑通常算术转换；本节用固定类型避免把规则混在一起。

移位边界与可移植性

  • 计数必须非负，并小于整型提升后的左操作数类型宽度。计数等于宽度、过大或负数都是未定义行为，不能用“自动对32取模”当作C规则。
  • 无符号左移在有效计数下按该类型的模数计算；无符号右移高位补0。
  • 本节C11中，负的signed值左移，或非负signed左移得到不可表示结果，不能按无符号规则处理；负数右移是实现定义，本片不执行这种例子。
  • 代码用sizeof(+bits) * CHAR_BIT取得本例提升后的宽度；count=32被范围检查拒绝，没有执行非法移位。guarded_shift保留初始化的0，不是非法移位计算出了0。

3. 同一个字节D6，unsigned是214，补码是-42

实验分别初始化两个对象：uint8_t u8=214、int8_t s8=-42。没有先把214强转为int8_t来依赖超范围signed转换。GDB实际读到两者的一个字节都为D6，即11010110；它们是两个对象，不是共用一块变量存储。

无符号8位的权从左到右为128、64、32、16、8、4、2、1：

11010110 → 128 + 64 + 16 + 4 + 2 = 214

8位补码最高位权为-128，其余位权不变：

11010110 → -128 + 64 + 16 + 4 + 2 = -42

最高位不是可以单独摘出来的负号。把D6误读成“负号+01010110”会得到-86，这是符号数值表示的错误套用，不是补码。

对于w位，unsigned范围为0…2^w-1，补码范围为-2^(w-1)…2^(w-1)-1。8位分别为0…255和-128…127；正负范围不对称。实验的int8_t／int16_t编码和本机int32表示与这里的补码模型一致；不把它推广为C11所有可选signed类型在所有实现上的表示声明。

4. 从+42构造-42的低8位编码

+42低8位为00101010。低8位取反得到11010101（D5），再加1得到11010110（D6）。原+42和原D6对照都保留，不能把原输入改成负数后假装“复制”。

实际C明确用无符号中间量和窄化：

inverted8 = (uint8_t)(~(uint32_t)magnitude);
negated8 = (uint8_t)((uint32_t)inverted8 + UINT32_C(1));

因此不是错误地断言~uint8_t只翻8位。这个构造说明编码关系，不是在执行可能溢出的任意signed取负表达式。

同宽补码最小值没有对应的正值；例如8位没有+128。但C中的int8_t先提升：本次-small_min实际在int32中得到128；不能忽略提升而说这条C表达式必定发生8位溢出。32位int最小值直接在32位int中取负则是另一回事，本片不执行它。

5. 扩宽：补0或复制符号位

uint8_t u8=214uint16_t zero_extended21400D6
int8_t s8=-42int16_t sign_extended-42FFD6

无符号扩宽高位补0；补码signed扩宽复制原最高位，保留原值。新目标占16位，旧源仍占8位，不能把源容量框直接拉长来冒充分配变化。动画复制低8位，并分别填入新的高8位；GDB实际内存字节为D6 00和D6 FF（地址升序）。这两个字节的内存顺序与位权图写00D6／FFD6不矛盾。

6. 转到unsigned窄类型：模2^w

实际wide_unsigned=0x00001234转成uint8_t，得到0x34（52），即4660模256。高位只是不进入目标，原32位源值并没有被清掉。

C11转到unsigned类型的规则是按目标可表示范围对应的模数转换，包括从负值转换。不能把这个规则直接套到超范围signed窄转换：后者是实现定义的结果或实现定义信号，本例不依赖它。

如果源的值能由目标类型表示，数值保持不变；是否“截掉一些物理高位”应放在具体表示和类型规则下解释，而不是把所有类型转换都叫作同一种截断。

7. unsigned模加与signed溢出不是同一种保证

本次uint32_t wrap_lhs=UINT32_MAX，与1u相加，实际wrapped=0。这里运算类型为32位unsigned，按模2^32计算是定义明确的C语义。动画中的边界外进位不是内存越界，也不是异常。

wrapped = wrap_lhs + UINT32_C(1);

对于uint8_t，别漏掉提升：本次u8_max=255，u8_max+1先得到int32的256；再显式转成uint8_t时才得到0。不是C先进行了一次8位unsigned加法。

对signed int32_t，INT32_MAX+1超范围，C11中的有符号算术溢出是未定义行为。某个硬件ADD的低32位、某个调试器表达式的结果、或某次未优化机器码表现，都不能变成C承诺的回绕结果。

本程序没有执行溢出的int32加法，而是先扩为int64安全计算，再检查范围：

wide_sum = (int64_t)signed_lhs + INT64_C(1);
if (wide_sum >= INT32_MIN && wide_sum <= INT32_MAX)
    signed_result = (int32_t)wide_sum;
else
    signed_rejected = 1;

这是程序主动写出的检查，不是C自动捕获signed溢出。实际wide_sum=2147483648，signed_rejected=1，signed_result仍为初始化的0，因为没有赋值。动画显示“拒绝产生int32结果”，不画出伪造的INT32_MIN或0作为signed溢出的结果。

反过来，int8_t small_max=127的small_max+1先提升为int32，本次实际为128，没有signed int32溢出，也没有自动窄回int8_t。要判断运算，必须先找实际运算类型，再找目标转换。
