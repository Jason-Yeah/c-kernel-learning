# 字节序：同一个数值的内存排列

[观看动画](byte-order.html) · [本章目录](index.html) · [完整 C](../experiments/byte-order.c) · [原始 JSON](../traces/byte-order.json) · [GDB 文本](../traces/byte-order-gdb.txt)

## 同一个值，不是同一种排列

uint32_t 的数值0x12345678按位权分为12、34、56、78。12是最高位字节，78是最低位字节；这不等于“低地址到高地址”的顺序。

本实验为Linux x86-64、8-bit byte、小端。同一个word的实际地址在一次采集内不变，读取它不会消耗或修改原字节。按地址升序读，得到78 56 34 12；小端把低位字节放在低地址。动画用高地址在上、低地址在下的竖向数组，所以最低地址的78在最下面，不要把画面上→下误认为地址升序。

## 大端编码，不是假装换了CPU

be_encoded[4]是同一程序的另一个数组，明确初始化CC。C程序用移位把12 34 56 78依次写到它的+0、+1、+2、+3。它具有大端字节顺序：高位字节在低地址，但本机CPU仍是小端。本片没有在大端CPU上采集，也不把两个不同C对象的地址画成同一个地址。

## 读回时要使用约定

| 操作 | 本次实际结果 |
| --- | --- |
| memcpy从word到uint32_t native_read | 0x12345678 |
| 将BE数组直接memcpy到本机uint32_t raw_read | 0x78563412 |
| 按BE规则移位、合并到decoded_be | 0x12345678 |

memcpy复制对象表示，不自动转换端序。不同结果来自字节的解释方式，不是内存损坏或异常。使用unsigned char读取对象表示合法；没有把可能未对齐的字节指针强转为uint32_t*再解引用。

字节序排列的是多字节对象的各个字节，不把每个字节的bit倒过来。0x12作为数值写作0001 0010，不因LE/BE编码而变成0100 1000；数值表示也不是对物理芯片bit线布局的测量。

## 连续的镜头

96秒、6个分镜。word数值和&word出现后一直保留；实际内存从第3镜头一直保留；BE数组从第4镜头一直保留到末帧。它们是跨分镜的同一DOM对象，只移动、重排，不整屏淡出再复制重建。位权组、临时probe和已不再需要的代码才局部退出。末帧保留原word和两列。

并排内存列是同一进程中的不同对象，各自放大；不按全局VA比例排列。每个对象容量固定4字节，完整真实地址可查。箭头、镜头与教学时间为解释设计，不表示GDB测到了总线或真实耗时。

## 复现与证据

先检查[完整程序](../experiments/byte-order.c)，再从项目根运行 npm run capture:byte-order。只采集这一份固定、安全程序；保持系统ASLR，核心转储限制仅作用于目标进程。

保存一次正常退出0的运行、12个停点；包含四次读取、四次BE数组写入和三次读回。页面实验台展示完整未删改C、所有原样命令和输出，可定位到对应的已提交观察状态。源码与[实际ELF](../traces/byte-order/program.elf)有SHA-256记录；静态网页不运行ELF或GDB。
